# Files Portable 성능 분석

분석 기준: 2026-09-11, 커밋 bda8fcc. 소스와 기존 NativeAOT 빌드 로그를 대상으로 분석했다. 앱 실행, 자동 UI 테스트, 파일 복사 실험, 코드 수정 및 재빌드는 수행하지 않았다. 따라서 아래 우선순위는 코드에서 확인한 비용과 영향 범위를 바탕으로 한 판단이며 실측 병목 순위나 개선율이 아니다.

배포 현황: Data 제외 415개 파일, 약 133.7 MiB. Files.exe 약 49.5 MiB. 파일 개수 자체로 실행 성능 저하를 판단할 수 없으며 필요한 DLL·PRI·XBF 삭제는 개선 방법이 아니다.

## 1. 포터블 설정 I/O

근거: src/Files.App/Helpers/Application/AppData.cs:143, :180, :202, :220, :297.

PortableSettings의 읽기는 매번 이름 있는 Mutex를 취득하고 Load()에서 JSON 파일 전체를 읽어 Dictionary로 변환한다. 쓰기는 같은 잠금 안에서 다시 읽고 전체 JSON을 저장하며 Flush(true) 후 파일을 교체한다. 인덱서 대입은 값이 같아도 변경으로 처리한다. 따라서 이 저장소를 조회하는 호출에는 반복 파싱과 동기 파일 접근 비용이 있으며 UI 스레드에서 호출되면 그 시간이 응답 지연으로 이어질 수 있다. 상위 서비스가 값을 캐시하는 경로도 있으므로 모든 설정 getter가 디스크에 접근한다고 단정하지는 않는다.

SaveSessionTabs()는 전체 탭 목록을 직렬화하고 목록과 선택 인덱스를 따로 저장한다(AppLifecycleHelper.cs:419). 실제 저장 호출 빈도와 경로별 시간 계측이 우선이다.

제안: 읽기 스냅샷과 변경 감지를 도입하고, 동일 값 대입을 생략하며, 탭 관련 연속 저장을 하나의 트랜잭션으로 묶는다. 지연 저장은 종료 시 확정 저장을 보장해야 한다. 현재 구현의 프로세스 간 병합, Mutex, 원자적 교체를 제거하는 단순 캐시는 금지한다.

검증: 두 창에서 서로 다른 설정을 동시에 수정한 뒤 모두 보존되는지, 강제 종료·재시작 복원, 저장 호출 수와 UI 지연을 확인한다.

## 2. 하단 통계의 반복 전체 순회

근거: src/Files.App/Views/Layouts/BaseLayoutPage.cs:275, :283, :978.

선택이 바뀔 때 UpdateSelectionSize()가 호출된다. 여기서 전체 목록을 ToList()로 복사하고 파일만 다시 ToList()로 추출한 다음 용량·파일 수·폴더 수를 여러 차례 순회해 계산한다. 선택 항목을 바꾸기만 해도 전체 N개 항목에 비례하는 작업과 임시 배열 할당이 생긴다. 분할 화면은 각 화면의 목록에 이 비용이 적용된다. 폴더 안의 실제 데이터를 다시 읽는 작업은 아니며 메모리 목록 집계다.

제안: 전체 통계는 목록 추가·삭제·크기 변경·필터 변경 때 갱신하고, 선택 변경에서는 선택 통계만 갱신한다. 첫 단계로 여러 순회를 한 번으로 합치고, 이후 증분 집계를 적용할 수 있다. 화면에 표시하는 대상과 숨김·필터·검색 결과의 의미를 유지한다.

검증: 1천·1만·5만 항목에서 선택 변경 지연과 할당량, 전체 선택/해제, 필터 변경 및 watcher 갱신 이후 통계 정확성을 비교한다.

## 3. 시작 시 조건 검사보다 먼저 실행되는 작업

근거: src/Files.App/Helpers/Application/AppLifecycleHelper.cs:121~156; Utils/Cloud/CloudDrivesManager.cs:29; Utils/Global/WSLDistroManager.cs:26.

OptionalTaskAsync(CloudDrivesManager.UpdateDrivesAsync(), 표시설정) 형태는 조건을 검사하기 전에 메서드를 호출한다. 도우미는 이미 생성된 Task를 받으므로 false여도 실행을 막지 못한다. 클라우드 탐지는 시작되고 WSL은 Task.Run 작업이 예약된다. 숨긴 기능이 자원을 쓰며 조건 false 경로에서는 해당 Task를 기다리지도 않는다.

제안: 조건을 호출 전에 검사하거나 Func<Task>를 받아 true일 때 생성한다. 뒤늦게 해당 섹션을 켰을 때 초기화하는 경로와 실패 로깅은 유지한다. WSL 구현은 레지스트리를 읽으므로 현재 코드만으로 WSL VM을 시작한다고 주장할 수는 없다.

검증: 해당 섹션을 모두 끈 상태와 켠 상태에서 초기화 호출 수, 첫 창 표시 시간 및 시작 후 CPU/디스크 활동을 비교한다.

## 4. 폴더 로딩 중 전체 목록 교체

근거: src/Files.App/ViewModels/ShellViewModel.cs:1125~1163, :2470~2484; Utils/Storage/Enumerators/Win32StorageEnumerator.cs:33, :107~113.

열거기는 첫 목록을 빨리 보여주기 위한 중간 콜백을 제공한다. 콜백마다 누적 목록을 반영하고, 1만 항목 이하에서는 중간 정렬도 수행한다. 반영 과정은 전체 목록 복사 → 필터 → UI에서 Clear/AddRange → Reset이다. 작은 배치가 여러 번 도착하면 이미 표시한 항목도 반복 처리한다. 실제 가상화 컨테이너 재생성 규모는 측정해야 한다.

제안: 첫 표시의 빠른 응답은 유지하면서 후속 반영을 일정 시간 단위로 합치고, 마지막 상태만 반영하도록 병합한다. 이후 선택/스크롤을 보존하는 차이 갱신을 검토한다. 현재 DataGrid/GridView의 다중 항목 알림 제약 때문에 Reset을 쓰고 있으므로 단순 AddRange 알림 교체는 피한다.

검증: 첫 항목 표시 시간과 전체 로딩 시간을 별도로 측정하고, 그룹·정렬·필터·빠른 폴더 전환·취소·선택 유지 회귀를 확인한다.

## 5. 썸네일 대기열

근거: src/Files.App/ViewModels/ShellViewModel.cs:743, :1526~1546; Utils/Storage/Helpers/FileThumbnailHelper.cs:17, :55; src/Files.App.Storage/Windows/Managers/STATask.cs:17~56.

비캐시 썸네일은 ShellViewModel별 8개 세마포어로 제한된다. 반면 공용 STA 풀은 12개 스레드와 unbounded Channel<Action>을 사용하며 RunPooled 호출에 취소 토큰이 없다. 세마포어 진입 전과 결과 처리 전에는 취소를 확인하지만, 큐에 들어간 작업을 실행 전에 취소하는 기능은 이 경로에 없다. 공유 풀은 다른 셸 아이콘 작업도 처리하므로 여러 화면에서 대기가 누적될 가능성이 있다. 실제 누적량은 아직 측정하지 않았다.

제안: 큐 진입/실행 전 취소 확인, 같은 경로·크기·옵션·파일 버전 요청의 중복 병합, 현재 화면 우선 처리 및 상한을 검토한다. 실행 중인 COM 썸네일 처리기를 강제로 중단해서는 안 된다. 동시 실행 수를 무조건 늘리는 것은 메모리와 디스크 경쟁을 악화시킬 수 있다.

검증: 이미지 폴더 빠른 스크롤과 연속 탐색에서 큐 길이, 취소된 요청의 실행 수, 현재 화면 썸네일 대기시간, private bytes를 기록한다.

## 6. 상태 표시줄 레이아웃

근거: src/Files.App/UserControls/StatusBar.xaml.cs:111~145.

ViewModel의 모든 PropertyChanged에 대해 통계와 재측정을 요청한다. _remeasureQueued로 동일 큐 구간의 요청은 이미 병합하지만, 실행 시 전체 표시 상태로 전환하고 UpdateLayout()을 강제 호출한다. 표시 폭에 영향을 주지 않는 속성도 이 경로에 들어온다.

제안: 실제 폭을 바꾸는 속성으로 한정하고 값이 같으면 재측정을 생략한다. 자연스러운 Measure/Arrange와 기존 SizeChanged 활용을 우선 검토한다. 하단 정보를 항상 표시한다는 요구는 유지한다.

## 7. 복사·이동 전 확인

근거: src/Files.App/Utils/Storage/Operations/FilesystemHelpers.cs:675~714.

대상별 Exists 검사와 FTP 조회를 루프에서 수행한다. 항목 수가 많거나 네트워크가 느리면 복사 시작 전 대기가 길어질 수 있다. 실제 복사 처리량 병목이라는 증거는 없으며, 사전 확인 시간과 데이터 전송 시간을 나눠 측정해야 한다.

제안: 먼저 단계별 계측을 넣는다. 필요하면 대상 폴더 목록을 한 번 읽는 방법 또는 제한된 병렬 조회를 검토하되 파일시스템별 동작을 분리한다. 최근 수정한 취소 게이트와 충돌 확인을 건너뛰거나 파일 작업을 무제한 병렬화하지 않는다.

## 별도: 개발/빌드 성능

기존 tab-name-settings-final.log에는 IL3054 제네릭 재귀 확장 중단 경고가 있다. BulkConcurrentObservableCollection<T>가 다시 BulkConcurrentObservableCollection<GroupedCollection<T>>를 가지는 구조가 근거다(Utils/Storage/Collection/BulkConcurrentObservableCollection.cs:18). 이는 런타임 탐색 지연과 별개로 NativeAOT 분석·코드 생성 및 크기에 영향을 줄 수 있다. 이 경고만으로 전체 빌드 지연의 주원인이나 절감 시간을 확정할 수 없다.

제안: 별도 작업에서 그룹 계층의 타입 구조를 검토하고 같은 환경에서 clean publish 시간, 증분 publish 시간, EXE 크기 및 경고 수를 비교한다. 빠른 개발 반복에는 영향 프로젝트 빌드를 사용하고 최종 배포에서 NativeAOT Publish를 확인한다.

## 실행 순서 및 측정 기준

첫 개선 묶음은 숨긴 기능의 초기화 방지, 통계 단일 순회/캐시, 불필요한 상태줄 재측정 축소가 적합하다. 설정 캐시는 기대 범위가 넓지만 프로세스 간 데이터 보존 설계를 먼저 검토해야 한다. 목록 갱신·썸네일 큐는 계측 결과를 보고 별도 변경한다.

측정은 동일 PC·동일 폴더·동일 설정에서 변경 전후 최소 5회 반복하고 중앙값과 최댓값을 기록한다. 반복 수를 충분히 늘린 경우 p95도 비교한다. 프로세스 시작과 첫 창 표시, 첫 항목 표시와 전체 로딩 완료, 복사 준비와 실제 전송 시간을 각각 분리한다. 첫 실행과 반복 실행의 캐시 조건도 구분한다.

이번 작업에서는 코드와 배포 파일을 변경하지 않았으며, 성능 향상 수치나 메모리 절감량을 주장하지 않는다. 자동 실행 검증 대신 사용자의 수동 검증 방침을 유지했다.
